## 1. Why this patch exists

0.3.0 shipped the Flow overlay, where-was-I + marks, the localhost API, and the MCP
server — and introduced one regression: **vision throughput dropped after the switch to
native WebP encoding** (issue #64). GPU utilization now spikes per frame instead of
holding steady, which is the signature of the encode step landing synchronously on the
vision hot path and serializing work that previously pipelined.

That regression is the reason 0.3.1 exists. Everything else in this patch is
low-risk polish that was already fully specified inside its issue (#59) or is trivial
(#65, the version-link half of #57). The feature-shaped issues (#69, #56, the
quick-actions half of #57, #54) are explicitly dispositioned out — see §2 — so this
patch stays shippable in days, not weeks, and does not block the 0.4.0 sessions arc.

### PR2 — #64 vision throughput regression (profile first, then fix)

**Phase A — profiling (mandatory before any fix, output recorded in `05`/`06`):**
1. Reproduce: measure frames-processed-per-minute and GPU utilization shape on the
   current tree vs. the last pre-WebP tag, same workload, same model.
2. Locate the WebP encode call site(s) relative to the vision dispatch path. Answer
   one question precisely: **does the encode block the next inference dispatch?**
   (Synchronous encode on the capture→vision thread, lock contention around the frame
   store, or encoder effort/quality settings are the three expected suspects, in that
   order.)
3. Record the numbers in the build-loop output before writing a line of fix code.

**Stop condition:** if profiling shows the slowdown is *not* on the encode path
(e.g. it's the degrade-to-text change from PR #58, or model-side), STOP and report —
do not fix a different regression under this PR's flag.

**Phase B — fix, in preference order (D5):**
1. Move WebP encoding off the vision hot path (async / worker / bounded queue) so
   capture→inference pipelines as it did pre-0.3.0.
2. If (1) is insufficient alone: reduce WebP effort/quality settings to the cheapest
   level that preserves the 0.3.0 size win.
3. Escape hatch only if (1)+(2) fail: config-gated revert to the previous format,
   default off, recorded in `07` as a known trade-off.

**PR2 acceptance:**
- Frames-processed-per-minute within **10% of the pre-WebP baseline** measured in
  Phase A, same workload.
- GPU utilization returns to a steady shape (no per-frame spike/idle sawtooth) under
  continuous capture.
- WebP remains the storage format (unless the escape hatch was invoked, in which case
  `07` documents why).
- No schema change, no new user-facing setting (the escape hatch, if built, is a
  config-file flag, not UI).
- Before/after numbers quoted in the PR description.

## 4. Pre-answered product decisions (D1–D9)

Settled here so the agent only stops on genuinely new ambiguity.

- **D1 — #59 resolution:** the issue's option 1. Recognized-text grows inline, full
  height, no internal max-height, no nested scrollbar. Single scroll context is the
  attention-friendly choice.
- **D2 — report filename:** `screensearch-report-YYYY-MM-DD-HHmm` in **local time**,
  existing extension unchanged. Collision within the same minute: append `-2`, `-3`, …
- **D3 — report footer:** one footer line block: app version, model id used for
  generation, time span covered, active filters. Plain text, no new settings toggle.
- **D4 — version link (#57 partial):** version string in the quick menu; clicking opens
  `https://github.com/nicolasestrem/screensearch-v2c` in the default browser. The
  load/unload-model and start/stop-vision quick actions do **not** land in 0.3.1.
- **D5 — #64 fix preference order:** async-encode off the hot path → cheaper encoder
  settings → config-gated format revert (escape hatch, default off). In that order;
  don't skip ahead.
- **D6 — reminders principle (binding on 0.3.2 design):** any systray/reminder work
  must be pull-based and non-shaming. A tray icon passively showing state is in-bounds;
  push notifications nudging the user are out-of-bounds unless explicitly opted into,
  and the default answer is "the passive icon is the whole feature."
- **D7 — #54 fold-forward:** close the issue; its substance (app/window-title keyword
  intelligence for AI-tool recall) becomes an input to the 0.4.0 sessions segmentation
  heuristic. No standalone implementation.
- **D8 — no migrations:** 0.3.1 makes zero schema changes. If a fix appears to require
  one, that fix is wrong for a patch — stop and report.
- **D9 — profiling artifacts:** Phase A numbers live in the `05`/`06` build-loop
  outputs and are quoted in the PR2 description; they become the baseline the
  acceptance criteria are measured against.

## 5. Risks

| Risk | Note |
|---|---|
| #64 root cause isn't the encode path | Covered by PR2's stop condition; the profiling phase exists precisely so we don't fix the wrong thing under a patch flag. |
| Async encode introduces a frame-loss window on crash | Bounded queue + flush-on-shutdown; acceptable for a recall tool where the diff gate already drops frames by design. Note it in the PR description. |
| Scope creep from deferred issues | The disposition table in §2 is the contract. If it isn't in PR2/PR3, it isn't in 0.3.1. |
| 0.3.2 never happens and auto-update slips past 0.4.0 | `07` carries the explicit sequencing note (auto-update before 0.4.0 ships); PR4's release notes remind users of one more manual download. |
