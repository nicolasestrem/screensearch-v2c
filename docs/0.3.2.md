# ScreenSearch V2c — 0.3.2 Roadmap: Product Shell (mini-arc)

> **Repo destination:** `docs/0.3.2.md` (sibling of `docs/0.3.1.md`).
> **Arc name:** **P7.2 — Product shell mini-arc** (lifecycle + interface).
> **Operating model:** identical to the 0.2.x/0.3.0/0.3.1 arcs — every PR follows
> `specs/04_CLAUDE_CODE_BUILD_PROMPT.md` (mandatory reading order, stop-at-ambiguity,
> verbatim verification, build-loop outputs `05`–`08`), and **recycles `specs/04` as the
> per-PR operating prompt**. PR1 extends `specs/04` to cover this arc.
> **Mini-arc constraints (hard):** **zero DB schema migrations.** New *settings* surface
> is allowed (unlike the 0.3.1 patch) but only where a PR section names it; settings
> restructuring is presentation-first (D7). Anything violating these constraints is
> deferred by definition.

## 1. Why this arc exists

Two forces converge on 0.3.2.

**The repo's own ledger.** The 0.3.1 disposition table (`docs/0.3.1.md` §2) and
`specs/07_KNOWN_GAPS.md` explicitly park three things here: **#69 auto-update** (row 96,
with the hard requirement that it lands *before* 0.4.0 so the sessions release reaches
existing installs automatically), **#56 systray + the #57 quick-actions remainder**
(row 97, bound by the pull-based / non-shaming principle), and the **hotkey cross-chord
conflict check** (row 100, parked for "the next Settings/hotkey rework — the 0.3.2
mini-arc is the natural home").

**The interface has outgrown its shell.** Three symptoms, one cause — the UI grew
feature-by-feature across 0.2.x/0.3.x without a shell-level pass:

1. **Scrollbars where they don't belong.** 0.3.1's #59 fix established the principle
   (one scroll context, the outer page scrolls) for one card; the rest of the app never
   got the same treatment.
2. **Intermittent misplaced elements.** The NavRail intermittently renders ghost /
   duplicated nav items at wrong vertical offsets (screenshot evidence on file). A
   rendering bug, not a design choice — it needs a reproduce-first investigation, not a
   blind CSS patch.
3. **Settings is a wall.** One flat route (`ui/src/routes/Settings.tsx`, ~1,190 lines),
   15 sections, ~60 fields — including settings that are *provably dead* (JPEG quality's
   own hint says "has no effect today"; `uia_run_on_interactive`'s true-branch is dead
   per gap #83). The maintainer can no longer say what half of them do; a user never
   could. This is the anti-thesis of the product's attention-friendly principles.

Lifecycle work (PR2–PR3) and interface work (PR4–PR5) are largely disjoint code, so the
arc stays parallelizable and shippable in weeks, not months — and it must, because 0.4.0
(sessions) is queued behind it.

### PR2 — #69 auto-update (Rust lane)

Release infrastructure: `tauri-plugin-updater` (Tauri 2), a **minisign keypair** (D2),
a `latest.json` update manifest published as a GitHub Release asset by the release
pipeline, and the passive update UX (D1).

Mechanics:
1. Wire the updater plugin with the public key baked into `tauri.conf.json`; endpoint =
   the GitHub Releases `latest.json` URL for this repo.
2. Release pipeline change: build signs the installer artifact with the updater key and
   emits `latest.json` (version, notes URL, signature, platform URLs).
3. UX per D1: check on launch (+ a manual "Check for updates" in the quick menu and the
   App settings section); when an update exists, a **quiet, persistent indicator** (nav
   rail badge + App section line "v0.3.3 available — restart to update"); download in
   the background; **install only on user-initiated restart**. No modal, no nag, no
   auto-restart, ever.
4. Manual steps (recorded in `07` before merge): generate the keypair; private key →
   CI secret + an offline backup the maintainer controls; document that **losing the
   private key strands every installed copy** on manual downloads again.

**PR2 acceptance:**
- A local end-to-end test: install a `0.3.2-pre` build, serve a signed manifest for a
  higher version, observe detect → background download → restart-installs. Evidence:
  the updater log lines + before/after `--version` output.
- Tampered/unsigned manifest is **rejected** (negative test shown verbatim).
- No update available → zero UI presence (the indicator only exists when true).
- Release notes text for `v0.3.2` states plainly: *this* release is still a manual
  download; auto-update delivers releases **from here on** (0.4.0 will be the first).
- Windows code signing (Authenticode/SignPath, `07` manual-steps) is explicitly **not**
  this PR: the minisign updater signature is not an installer certificate. The gap row
  stays open.

### PR4 — Shell layout hardening (UI lane; reproduce first, then fix)

**Phase A — reproduce (mandatory before any fix, recorded in `05`/`06`):**
1. Reproduce the **NavRail ghost/duplication** glitch (nav items rendered again at odd
   vertical offsets mid-rail — screenshot evidence in the issue/roadmap). Identify the
   trigger: route transition, WebView2 compositing, CSS transform/containment on the
   rail, or virtualized re-render. Record exact repro steps.
2. Inventory every scroll context per route (the five routes + Settings) and every
   nested-scroll region; inventory layout-shift sources on load (skeletons that don't
   reserve space, late-loading status chips, font swap).

**Stop condition:** if Phase A shows the ghost-rail glitch is an upstream WebView2
compositing bug not addressable in app code, STOP on that item, record it in `07` with
the cleanest CSS-level mitigation found, and continue with the rest of the PR.

**Phase B — the shell layout contract (D9), enforced app-wide:**
- **One scroll context per route**: nav rail and status rail fixed; only the content
  pane scrolls; **no nested scrollable regions** (the #59 principle, everywhere).
- **No horizontal scrollbar** at any supported size (1280×720 minimum → ultrawide,
  100/125/150% DPI).
- **No cumulative layout shift on load**: skeletons reserve final dimensions; status
  chips have stable widths; toasts/banners overlay rather than push (except the
  readiness banner, which may reserve).
- Fix the ghost-rail glitch per Phase A findings.

**PR4 acceptance:** Phase A repro + root cause recorded before fixes; after Phase B, a
screenshot matrix (five routes × {1280×720, 1920×1080, 3440×1440} × {100%, 150%})
shows zero nested scrollbars, zero horizontal scrollbars, stable rails; the ghost-rail
bug demonstrably gone (or `07`-dispositioned with mitigation per the stop condition);
no visual identity drift — tokens only, per `UI_REFERENCE`.

### PR5 — Settings IA overhaul (UI lane, after PR3 + PR4)

The wall becomes two tiers (D6), on top of PR4's hardened shell:

- **Essentials (always visible):** Capture (interval, monitors, event-driven master
  toggle) · Hotkeys (overlay chord, mark chord, overlay results, dwell — **plus the
  gap-#100 inline cross-chord conflict warning**) · Privacy (excluded apps, pause on
  lock) · Models (vision/answer pickers, show thinking, load/unload) · Storage
  (retention days, max width) · **App** (new home: run at startup, close-to-tray,
  update status/check, version + repo link) · Data (local API toggle/port/token,
  export).
- **Advanced (collapsed per group, one expander each):** Capture tuning (change
  threshold, debounce, min interval, idle threshold, fallback interval, per-event
  toggles) · Text source / UIA (all remaining knobs) · Enrichment & scheduling ·
  Performance throttle (+ live CPU/GPU readout) · Text filtering (+ per-app suppression
  readout) · Reports & retrieval · Inference engine (sidecar).
- Every section opens with **one plain-language sentence** stating what it's for and
  when a normal person would touch it (voice per `UI_REFERENCE` §9).
- **Dead-setting removals (D8):** JPEG quality and `uia_run_on_interactive` leave the
  UI; their config keys are tolerated-and-ignored on load (no error, no migration, no
  write-back requirement). Gap #83 gets its ✅.
- **No key renames, no semantic changes** (D7). This PR moves and explains; it does not
  redefine.

**PR5 acceptance:** tier membership matches D6 exactly (within-tier ordering is the
implementer's); collapsed-by-default Advanced state persists sensibly (per-session is
acceptable; no new persistence machinery required); the conflict warning fires when
overlay and marks chords are set equal and clears when they differ (shown live); a
config file containing the two removed keys loads without error; keyboard navigation
and a11y pass per `UI_REFERENCE` §7; the page renders with **no nested scrollbars**
(PR4's contract holds).

## 4. Pre-answered product decisions (D1–D12)

Settled here so the agent only stops on genuinely new ambiguity.

- **D1 — update UX is pull-based:** check on launch + manual check; quiet persistent
  indicator when (and only when) an update exists; background download; install on
  user-initiated restart. No modals, no nags, no auto-restart. This is 0.3.1's D6
  principle applied to the updater.
- **D2 — updater infrastructure:** `tauri-plugin-updater`, minisign keypair, manifest
  (`latest.json`) as a GitHub Release asset on this repo. Private key: CI secret + an
  offline maintainer-controlled backup, documented in `07` manual steps **before** the
  first signed release. Key loss = users stranded; treat the backup as a release
  blocker.
- **D3 — tray scope:** passive state icon (capturing / paused / error); menu = Open,
  Pause/Resume capture, Load/Unload answer model, Start/Stop vision, Check for updates,
  Quit. Close-to-tray **ON by default** with a one-time explanatory toast and an App
  setting to disable. Run-at-startup exists, **default OFF**.
- **D4 — no push, restated as binding:** the tray's passive state display is the entire
  "reminder" feature of #56. No notifications, no nudges, no badges that count things.
  Anything push-shaped is out of this arc and requires its own opt-in design
  conversation (per `02 §7`).
- **D5 — sister-app reuse is a reviewed import:** read `screensearch-v2@d865c3d` and
  `docs/design/p2-shell.md`; adopt its four hardening patterns where they apply; V2c is
  clean-slate, so no wholesale code copy; its notification behavior is excluded by D4.
- **D6 — Settings two-tier IA:** tier membership as written in PR5 is **settled**;
  within-tier ordering and visual grouping are implementation freedom. A settings
  search box is **deferred** (the restructure should make it unnecessary; revisit in
  0.4.x only if it isn't) — record in `07`.
- **D7 — presentation-first restructure:** zero settings-key renames, zero semantic
  changes to any retained setting. The Settings *store* shape is untouched except for
  D8's removals and PR3's additions.
- **D8 — dead-setting removal mechanics:** a setting may be removed in this arc only if
  it is provably inert (JPEG quality by its own hint; `uia_run_on_interactive` per gap
  #83). Removal = UI removal + config-load tolerance for the orphaned key. If the
  config layer would error on an unknown/orphaned key, keep the field
  deserialized-but-unused instead of building migration machinery.
- **D9 — shell layout contract:** one scroll context per route; fixed rails; no nested
  scroll regions; no horizontal scrollbars ≥1280×720 at 100–150% DPI; no layout shift
  on load (skeletons reserve space). This contract enters `UI_REFERENCE` as
  acceptance-grade language and binds all future UI work, not just this arc's.
- **D10 — zero DB schema migrations:** if any piece of this arc appears to need one,
  that piece is wrong for a mini-arc — stop and report.
- **D11 — #88 fold-forward:** label + comment, keep open as the 0.4.0 anchor issue for
  AI-tool recall; its user-vs-agent role separation becomes a sessions-schema
  requirement (recorded in `07` next to gap #98). No standalone implementation.
- **D12 — no visual redesign in this arc:** PR4/PR5 are structural (layout + IA). The
  aesthetic direction (`UI_REFERENCE` §1: warm graphite, one bold accent, scanline
  identity) is untouched. If a token-level visual refresh is wanted, it's a separate
  conversation that amends `UI_REFERENCE` §1 first — record the possibility in `07`,
  don't smuggle it in.

## 5. Risks

| Risk | Note |
|---|---|
| Updater key loss or leak | D2 makes the offline backup a release blocker; leak requires key rotation via a manually-shipped release — document the rotation path in `07` when the key is created. |
| First-release updater bugs are unfixable-by-updater | True by construction (0.3.2 installs are the first updater-capable population). Mitigate with the PR2 end-to-end + negative tests before tagging; worst case is another manual download, which is today's status quo. |
| Ghost-rail glitch is upstream (WebView2) | PR4's stop condition: record + best CSS mitigation, don't burn the arc on it. |
| Settings restructure breaks muscle memory | Two tiers preserve every retained setting; section intros are the map. No renames (D7) means docs/API/config references stay valid. |
| PR3/PR5 coupling (tray settings need a home) | Sequencing handles it: PR3 may land keys with provisional placement; PR5 owns final placement. |
| Scope creep toward a visual redesign | D12 is the fence. Structural only. |
| Rust lane and UI lane drift apart | Both lanes re-read the tree per `specs/04` each session; merge each PR before the next in its lane. |
